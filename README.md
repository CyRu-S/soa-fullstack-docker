# ParcelDesk — Courier Pickup

A small React + Bootstrap frontend connected to the existing Spring Boot courier API.

## Folders

- `backend/`: the original `CrudServiceProject`, including its Maven wrapper and source files.
- `frontend/`: React components (JSX), CSS, Bootstrap, and Vite.

The existing Git history and remote are retained at this workspace root so both projects can be tracked together. No commit or push is performed by the setup.

## Run locally

Requirements: JDK 25, Node.js 22.19 or later, and PostgreSQL. The backend's database configuration is in `backend/src/main/resources/application.properties`. Ensure that the configured database exists and PostgreSQL is running. The backend also retains its existing Eureka configuration.

Start the backend in one terminal:

```powershell
cd backend
.\mvnw.cmd spring-boot:run
```

Start the frontend in another terminal:

```powershell
cd frontend
npm install
npm run dev
```

Open **http://127.0.0.1:5173**. The frontend sends `/api/courier/...` requests through Vite to **http://localhost:8081/courier/...**, so no backend CORS changes are needed for local development. Override the target with the `BACKEND_URL` environment variable before starting Vite if needed.

The UI supports adding, viewing, editing, deleting, searching, and filtering pickups, with loading states and success/error messages. IDs are generated by the backend. `status=false` is shown as Pending and `status=true` as Picked up. Frontend checks require names and addresses, and parcel weight must be between 0.01 and 1,000 kg. Sender-name validation also runs on the backend for add/update through `@Valid`: names must be nonblank, contain only A–Z/a–z letters and spaces, and be at most 100 characters. Invalid names return HTTP 400 with a descriptive validation error. Backend validation for the remaining fields is still pending.

## Check the frontend build

```powershell
cd frontend
npm run build
npm run preview
```

Preview is at **http://127.0.0.1:4173**, with the same API proxy. The generated `frontend/dist` folder contains static assets. The frontend Docker image includes an Nginx `/api` reverse proxy; the Vite development/preview proxy is not included in those static assets.

Swagger UI is at **http://localhost:8081/swagger-ui/index.html** when the backend is running.

## React frontend structure

- `frontend/src/main.jsx`: React entry point.
- `frontend/src/App.jsx`: application state and courier operations.
- `frontend/src/components/`: pickup form, register, and delete confirmation.
- `frontend/src/api.js`: requests to the Spring Boot API.
- `frontend/src/styles.css`: existing Bootstrap styling and custom design.

`frontend/index.html` is the minimal Vite entry document; the interface is rendered by React components.

## Run with Docker Compose

Start Docker Desktop with Linux containers enabled. From the workspace root:

```powershell
docker compose up --build -d
```

Compose builds the React frontend and Java 25 backend, and starts an isolated PostgreSQL 17 database. No local Java, Node.js, or PostgreSQL installation is needed for this mode. Database connection settings are supplied through environment variables, and Eureka is disabled inside Compose. The existing local-development properties are retained.

- Frontend: **http://localhost:3000**
- Backend API: **http://localhost:2025/courier/displayall**
- Swagger UI: **http://localhost:2025/swagger-ui/index.html**

The containers are named `postgres-db`, `docker-springboot`, and `docker-react`, and share `springboot-postgres-net`. Backend port mapping is `2025:8081`; frontend mapping is `3000:80`. Within Docker, Nginx forwards `/api/courier/...` to `backend:8081/courier/...`, and the backend connects to `postgresdb:5432`. PostgreSQL is available at `localhost:5433` because local PostgreSQL already uses port 5432. PostgreSQL 17 and the existing database volume/credentials are retained. The backend and frontend restart on failure. Simple `depends_on` controls startup order; allow a few seconds for the database and backend to become ready before using the UI.

To change ports, credentials, or image names, copy `.env.example` to `.env` and edit it before starting Compose. Database initialization credentials apply when the named database volume is first created; editing them later does not change an existing database user's password. The Compose database starts empty and does not import your local PostgreSQL records.

```powershell
docker compose ps
docker compose logs -f backend
docker compose down
```

`docker compose down` stops/removes the containers but retains records in the named `postgres_data` volume. Adding `--volumes` removes that database data.

Application image names are `arpandutta030705/docker-frontend-2400033066:latest` and `arpandutta030705/docker-backend-2400033066:latest`. Compose retains local build contexts so `docker compose up --build -d` works before the images are published.

## GitHub Actions and Docker Hub

Repository: https://github.com/CyRu-S/soa-fullstack-docker

The workflow in `.github/workflows/docker-fullstack.yml` follows a single job: checkout, set up Buildx, log in to Docker Hub, and build/push the backend and frontend images. It builds both images for pull requests without logging in or publishing. Pushes to `main` build and publish both `latest` tags, matching the default Compose image references.

Before the first publishing run, add these repository secrets under **Settings > Secrets and variables > Actions > New repository secret**:

- `DOCKERHUB_USERNAME`: `arpandutta030705`.
- `DOCKERHUB_TOKEN`: a Docker Hub access token with permission to push to both image repositories.

Commit and push the full project, including `backend/`, `frontend/`, and `.github/workflows/`, to `main`. Monitor **Actions > Docker Fullstack** and confirm both images appear under the Docker Hub namespace after the run succeeds. Do not commit your access token or `.env` file.

To run the published images instead of building locally:

```powershell
docker compose pull backend frontend
docker compose up -d --no-build
```
